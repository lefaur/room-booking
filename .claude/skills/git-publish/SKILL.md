# Коммит и пуш

Вызов навыка — это и есть разрешение коммитить и пушить. Без явной просьбы пользователя (или
`qa-task` по его слову) навык не запускается: коммит — решение пользователя.

## Шаг 1. Что меняется

```bash
git status --short
git diff --stat
git log --oneline -5      # стиль сообщений и что уже ушло
```

Прочитать дифф целиком (`git diff`, для новых файлов — сами файлы). В коммит идёт только то, что
относится к задаче. Посторонние правки (чужая незаконченная работа, отладочный `print`, `KEEP_DATA=1`
в конфиге) — спросить пользователя, а не включать молча и не откатывать.

## Шаг 2. Чего в коммите быть не должно

- секреты: `.env`, токены, пароли, `Authorization: Bearer …` в логах и примерах, приватные ключи —
  `git diff --cached | grep -iE "token|secret|password|bearer|BEGIN .*PRIVATE"` и глазами по каждому
  попаданию (тестовые пароли в `.feature` — норма, настоящие — нет);
- артефакты прогонов: `reports/`, `allure-results/`, `__pycache__`, `node_modules/` (они в `.gitignore`;
  попали в `git status` — значит игнор сломан, чинить его);
- личные данные: адреса почты, имена, пути домашних папок вне тестовых данных;
- файлы больше пары мегабайт, кроме скриншотов документации.

Нашлось — остановиться и сказать пользователю. Секрет уже в истории — не переписывать её самому:
сказать, что ключ надо отозвать.

## Шаг 3. Проверка перед пушем

Менялся код (`services/`, `web/`, `tests/`) — полный набор зелёный на свежем стенде:

```bash
docker compose up -d --build --wait
docker compose run --rm tests
```

Менялся интерфейс — переснять инструкции (`sh run.sh -t @instruction`, см. навык `user-guide`) и
закоммитить снимки вместе с кодом. Только документация — прогон не нужен, ссылки в `.md` проверить.

Красное — не пушить. Сказать, что упало, и вернуться к работе.

## Шаг 4. Коммит

Добавлять файлы по путям, а не `git add -A` вслепую: `git add <пути>`, затем `git status --short`
— в индексе ровно то, что задумано.

Сообщение — по-русски, как в истории репозитория:

```
<область>: <что сделано>          ← первая строка до ~90 знаков; область — CI, web, тесты, README…

- зачем и что именно, по пункту на изменение
- найденный и исправленный дефект — что было, почему

Co-Authored-By: <строка соавтора, которую даёт окружение Claude Code>
```

Сообщение — через heredoc (`git commit -F - <<'EOF' … EOF`), не через `-m` с переносами.

Нельзя: `--no-verify`, `--amend` уже запушенного коммита, `push --force`, `reset --hard`, правка
чужих коммитов. Хук упал — исправить причину и сделать новый коммит.

## Шаг 5. Пуш

Ветка `main` — единственная в репозитории, пользователь разрешил пушить в неё. Для крупной или
спорной правки — ветка `<область>/<коротко>` и вопрос пользователю, нужен ли pull request.

```bash
git push
```

Отказ (non-fast-forward) — `git pull --rebase`, разобрать конфликты, снова тесты, снова пуш. Не
`--force`.

## Шаг 6. CI

Workflow `tests` идёт на каждый пуш в `main` (5–8 минут). API GitHub без токена — 60 запросов в час,
поэтому не опрашивать в цикле, а проверить один-два раза:

```bash
curl -s https://github.com/lefaur/room-booking/actions \
  | grep -o 'aria-label="[^"]*Run [0-9]* of tests[^"]*"' | head -1
```

`completed successfully` — готово, отчёт на https://lefaur.github.io/room-booking/. `failed` — открыть
ран, найти шаг; падение тестов — артефакт `reports` (Allure, логи сервисов). Чинить — новым коммитом.

## Итог пользователю

Хеш и первая строка коммита, что в него вошло (одной-двумя строками), результат прогона перед
пушем и статус CI. Не видел результат CI — так и сказать: «CI запущен, результата ещё нет».
