# Написание автотестов

Вход — что проверить (матрица из `qa-task` или прямая просьба). Выход — сценарии, которые падают при
сломанной системе и зелёные на рабочей, и короткий отчёт: какие файлы, какие шаги новые.

Перед работой прочитать `docs/FRAMEWORK.md`, разделы «Механизмы», «Новый сценарий: пошагово», «Теги».

## Порядок

1. **Сценарий словами.** Сначала `.feature`, на русском (`# language: ru`), шаги из готовых:
   `grep -rhn "^@step" tests/features/steps/`. Новая фраза — только если готовой нет; формулировка в том же
   стиле: API — `пользователь "<ярлык>" …`, браузер — `в браузере …`, БД — `в БД …`.
2. **Клиент API** (`framework/api.py`) — метод без проверок, только путь и тело.
3. **Модель ответа** (`framework/models.py`) — наследник `Contract`, поля ровно как в ответе сервиса:
   лишнее поле в ответе — падение, это и есть проверка контракта.
4. **Шаги** (`features/steps/<область>_steps.py`), хелперы из `framework/support.py`:
   `actor()` (участник по ярлыку, создаётся при первом упоминании), `expect(resp, status)`,
   `parse(Model, resp)`, `day_of()` (русские даты: «завтра», «пн рабочей недели»), `office_datetime()`.
5. **UI** — класс экрана в `framework/ui/pages.py` с методами-действиями; шаг не трогает локаторы.
   Локатор — только `data-testid`; нет атрибута — добавить его во `web/src`, а не писать CSS-селектор.
6. Прогнать файл: `docker compose run --rm tests behave features/<область>/<файл>.feature`, затем область
   через `sh run.sh -t @<область>` (параллельно, с блокировками).

## Канон

**Данные.** Каждый сценарий создаёт своих пользователей и свои ресурсы с уникальными именами
(`data.unique_name`, `actor`). Брать «какую-нибудь» существующую сущность стенда нельзя: соседний
сценарий её поменяет.

**Предусловия** («Дано») — через SQL-подготовку (`framework/prepare.py`, `with preparation(context)`),
если их побочные эффекты (письмо, событие в очереди) сценарию не нужны. Нужны — через API, отдельной
фразой (`… зарегистрировался через API`). Новый вид сущности — в `prepare.py` и в `CREATED_BY` /
`STATEMENTS` уборки `framework/cleanup.py`, иначе сценарий оставит мусор.

**Общее состояние.** Меняешь правила или календарь — тег `@settings` / `@calendar`: монопольная
блокировка и откат после сценария. Без тега шаг смены правил падает сразу. Новое общее состояние —
в `SHARED_STATE` `framework/locks.py`, а не `@serial`.

**Ожидание.** Асинхронный результат (письмо, сообщение бота, джоба) — `wait_until` из
`framework/infra.py`, не `time.sleep`.

**Ассерт.**

- Ожидаемое значение — из постановки и кода сервиса, не скопировано из фактического ответа.
- Равенство, а не `>=` / `in`, если система обещает точное значение.
- Проверяется то, что обещано: статус *и* тело, запись в БД *и* что лишнего не появилось.
- Без `try` вокруг проверки, без ретраев до зелени, без `@skip` «пока не починят».

**UI.** Браузер проверяет видимое; данные готовятся через БД/API, итог сверяется по API. Время на
экране — офисное (браузер нарочно в другом часовом поясе). Мобильная вёрстка — тег `@mobile`.

**Теги** — область (`@booking`, `@auth`, …) + `@ui` для браузера. Для выборки в CI теги должны
отвечать на вопрос «что сломалось».

## Нелогичное поведение

Если система ведёт себя странно (отрицательное число, «занято» для своей брони, разные форматы одной
даты) — не закреплять ассертом как норму. Строка в итог задачи и в `docs/user-guide/questions.md`;
пользователю — вопрос, ожидание какое.

## Чеклист перед сдачей

- [ ] Сценарий падает, если сломать проверяемое условие (мысленно или правкой сервиса на минуту).
- [ ] Все сущности свои; после прогона в БД не осталось строк сценария (`KEEP_DATA` не включён).
- [ ] Новые фразы шагов не матчатся в чужие определения (`behave --dry-run` без ошибок `AmbiguousStep`).
- [ ] Общее состояние — с тегом блокировки.
- [ ] Область зелёная в параллельном прогоне `sh run.sh -t @<область>`, а не только одним файлом.
